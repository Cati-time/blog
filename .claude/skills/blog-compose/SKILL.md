# blog-compose — 취재해서 쓰는 글: 뼈대 → 질문 → 살 붙이기 → 사실 확인

이 스킬의 약속은 셋이다.

1. **거짓말을 쓰지 않는다.** 글의 숫자와 «좋아졌다» 같은 효과는 저장소에서 센 값으로만 쓴다. 못 쟀으면 필자의 판단이라고 밝힌다.
2. **사실은 원천에서, 글은 여기서.** 블로그 세션은 다른 저장소를 읽기만 한다. 조사와 사실 확인은 그 저장소에서 일하는 세션(원천 세션)에 요청한다.
3. **«어떻게» 보다 «왜».** 모르는 «왜» 는 사용자에게 묻기 전에 원칙에서 도출하고 원천에서 조사한다. 사용자에게 묻는 것은 사용자만 아는 것(의도 · 판단 · 겪은 일)뿐이다.

| --- | --- |

## 역할

| 누구 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 사용자(필자) | 주제 · 독자 · 편 구성 · 흐름, 판단 문장, 발행 결정 | — |
| 블로그 세션(이 스킬) | 뼈대 · 질문 · 초안 · 그림, 숫자 다시 세기, 기록 · 커밋 | 다른 저장소 수정 · push · 사실 지어내기 |
| 원천 세션 | 그 저장소에서 사실 조사 · 숫자 세기 · 사실 확인 표 | 블로그 파일 수정 |

## 글의 원칙 — 네 단계 모두

- **독자 · 말투**: 사용자가 정한 대로. 정하지 않았으면 일반 개발자 독자, 필자 1인칭, 합니다체.
- **숫자는 센 것만**
  - 효과(«줄었다 · 빨라졌다 · 쉬워졌다»)는 같은 조건의 비교가 있을 때만 숫자로 쓴다. 없으면 필자 판단으로 쓰고 «따로 세어 두지는 않았지만» · «같은 조건으로 잰 기록은 아직 없습니다» 같은 단서를 붙인다.
  - 사용자의 주장이 실측과 다르거나 실측이 없으면 그대로 쓰지 않는다. 실측을 먼저 보여 주고 «판단 + 단서» 문장을 제안한다.
  - 기간: 첫 커밋부터 끝 커밋까지의 달력 기간을 작업 시간처럼 쓰지 않는다. 커밋 시각으로 추정하고(사이가 1시간 넘게 비면 쉰 것으로, 작업 묶음마다 앞에 15분을 더함) 방법을 본문에 밝힌다.
- **이중 측정**: 글에 넣을 숫자는 블로그 세션과 원천 세션이 **따로** 센다. 상대 값을 보지 않고 센다. 갈리면 원인(범위 · 정의 · 시점 · 출처 없음 · 재현 안 됨)을 찾아 맞춘다. 원인을 찾고도 ±3 안쪽 차이만 남으면 «약» 으로 쓴다.
- **시점**: 흐름을 보여 주는 시점은 «처음 · 그다음 · 지금» 같은 상대 표현을 먼저 쓴다. 달 이름은 글에 꼭 필요할 때만 쓴다(그림 라벨도 같다).
- **공개 안전**: 이 저장소는 공개이고 push 가 곧 배포다. 글 · 그림 · **이 저장소의 커밋 메시지**에 내부 저장소 이름 · 결정 기록(ADR) 번호 · 커밋 해시 · 티켓 · 사람 이름 · 개인정보 예시를 쓰지 않는다. 내부 근거는 저장소 밖 노트에 둔다. 사내 메시지에서 결정 기록 번호를 쓸 때는 스코프까지 쓴다(번호가 스코프마다 겹칠 수 있다).

## 4단계

### ① 뼈대

1. 사용자에게 주제 · 독자 · 편 구성 · 흐름을 듣는다. 시리즈면 편마다 한 줄 목표를 정한다.
2. 뼈대를 쓴다 — 섹션마다 «무엇을 보여 주나 · 필요한 사실과 숫자 · 그림 후보». 사용자에게 보여 확정받는다. 구조와 순서는 사용자 몫이다.
3. 원천 세션을 찾는다. 사용자가 지정한 세션이 있으면 그것, 없으면 세션 목록에서 그 저장소의 세션을 찾아 사용자에게 확인한다. 메시지는 세션 **id** 로 보낸다(제목은 바뀐다).
4. 원천 세션에 «뼈대 · 조사 요청»을 보낸다(`templates.md` §1). 사용자 방향 원문, 뼈대, 섹션별 요청(값 · 정의 · 근거 · 기준 ref＠sha)을 담고, «메모 값을 보지 말고 직접 세기» 와 공개 안전, 회신 주소를 적는다.
5. 계획은 `../blog-notes/plans/<시리즈>.md` 에 적는다. 사용자의 결정과 바뀐 방향을 날짜와 함께 남긴다.

### ② 질문

1. 회신을 읽고 빈 곳 · «왜» · 모순을 다시 묻는다. «왜» 는 원칙(예: 정본은 한 곳)에서 먼저 도출해 보고 원천에 근거를 찾아 달라고 한다.
2. 핵심 숫자는 블로그 세션이 직접 다시 센다(원천 저장소는 `git show` · `git grep` 으로 읽기만). 갈리면 원인을 적어 원천과 맞춘다. **조사 회신의 숫자는 다시 세기 전에는 초안에 넣지 않는다.** 다시 세지 못한 숫자를 꼭 써야 하면 사실 확인 요청에 «단독» 이라고 표시해 둔다. 조사 회신에서 따로 세지 않고 옮긴 숫자가 사실 확인에서 가장 많이 고쳐졌다.
3. 원천의 명세와 코드가 어긋난 것(드리프트)을 찾으면 원천 세션에 알린다. 그 저장소의 소통 규칙(예: 법제처 · 감독 경로)을 따른다.
4. 조사 메모는 `../blog-notes/research/<주제>.md` 에 둔다.

### ③ 살 붙이기

1. 글 파일: `npm run new "제목" slug --category <…> --platform <…> --tags a,b --draft`. 처음부터 `draft: true` 다.
2. 섹션마다 «왜» → 실제 사례(코드 · 커밋) → 숫자 → 대가 순으로 쓴다. 좋아지지 않은 것과 대가도 쓴다.
3. 그림은 `scripts/make-charts.mjs` 에 구간을 더해 SVG 로 만든다. 그림의 숫자는 글의 숫자와 같은 데이터에서 나온다.
4. `npm run build` 통과 → 커밋(`post:` 새 초안 · `edit:` 고침) → dev 서버로 보여 준다.
5. 사용자의 수정 지시는 반영하되, 사실과 부딪히면 실측을 먼저 보여 주고 함께 정한다.

### ④ 사실 확인

1. 원천 세션에 «사실 확인 요청»을 보낸다(`templates.md` §2). 산출물 경로＠sha, 지난 회차 뒤 바뀐 곳(diff 명령과 줄 번호), 번호 붙인 주장 목록, 표 양식을 담는다. 첫 회차는 `범위: 추가`, 고친 줄만 다시 보는 회차는 `범위: 재확인` 이다.
2. 회신 표(`templates.md` §3)의 «고침» 은 블로그 세션이 다시 세어 대조한다. 맞으면 반영하고, 다르면 근거를 들어 되묻는다(다음 회신에 정정 줄로 돌아온다).
3. 반영 → build → 커밋(`edit:`). **커밋 메시지에는 집계만** 쓴다(주장 수 · 그대로 · 고침 · 뺌 · 이중 측정). 표 원문과 «blog 처리» 는 `../blog-notes/fact-checks/<slug>-R<n>.md` 에 둔다(`templates.md` §4).
4. 사용자 지적으로 글이 크게 바뀌면 그 부분만 다음 회차로 확인한다(머리: `범위: 추가 · 발단: 사용자 지적`).
5. 팀이 사실 확인 지표를 모으면(예: 법제처 취합 지표) 회차 표 위치와 sha 를 알린다.

## 발행

- 사용자가 «발행» 이라고 할 때만 한다.
  1. (선택) `humanize-korean` 스킬로 윤문한다. 숫자 · 인용 · 판단 + 단서 문장은 보존한다.
  2. `pubDate` · `draft: false` · 시리즈 상자 링크를 바꾼다.
  3. build → `post:` 커밋 → «push 하면 배포됩니다».
- push 뒤에는 배포(Actions)와 공개 주소를 확인한다. 막 배포된 직후에는 CDN 이 옛 응답을 최대 10분 들고 있을 수 있다.
- 발행 뒤 정정이 생기면 `edit:` 로 고치고, 지표를 모으는 팀이면 «발행 뒤 정정» 으로 알린다.

## 하지 않는 일

- 다른 저장소 수정 · push
- 원천 세션의 판정을 다시 세지 않고 옮기기
- 사용자의 판단을 사실처럼 쓰기, 근거 없는 숫자
- 사용자가 «발행» 이라고 하기 전에 초안 해제
