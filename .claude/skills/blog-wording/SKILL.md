# blog-wording — 개발자가 쓰는 말로

> **규범은 헌법이 갖는다** — `docs/constitution/RULES.md` R-BLOG-WORDING(글 레인 게이트 `check:wording --strict`) · WORKFLOW 칸 16 «용어 손봄». 이 스킬은 절차다 — 어긋나면 헌법이 이긴다.


이 스킬의 약속은 셋이다.

1. **근거 없는 대체어를 지어내지 않는다.** 바꿀 말은 용어집에 있는 것만 — 사용자 결정이거나, 한국어 기술 블로그에서 실제로 센 말.
2. **사용자 결정이 근거보다 우선한다.** 실측이 달라도 사용자가 정한 말을 쓴다. 다만 실측이 어긋나는 쓰임은 사용자에게 보여 준다.
3. **용어 · 말투만 고친다.** 숫자 · 사실 · 판단 + 단서 문장은 그대로. 고칠 문장은 사용자 확인 뒤 반영한다.

| 무엇 | 정본 |
| --- | --- |
| **용어(대표 이름 · 다른 이름 · 쓰지 않는 말 · 정의)** | **`src/data/glossary.json`** — 블로그 `/glossary/` 페이지 · 이 검사 · 글이 같은 문구로 읽는다 |
| 찾는 정규식 | `scripts/check-wording.mjs` 의 `TERMS` — 줄마다 `glossary: '<대표 이름>'` 으로 잇는다. 원천 근거(횟수)는 glossary 의 `evidence`. 표로 보기: `npm run check:wording -- --list` |
| 말투 규칙(규칙형 «~한다» · 억지 피동) | 같은 파일의 `PLAIN_END` · `FORCED_PASSIVE` |
| 실측 원천 · 수집물 · 집계표 | 저장소 **밖** 노트 폴더 `../blog-notes/style/` (수집물은 공개 금지) |

## AI 티 — 정규식으로 잡히는 것 (2026-11-23)

`humanize-korean` 분류(ai-tell-taxonomy · 85 패턴)를 이 저장소 글 22 편에 돌려 **오탐 30 % 이하만** `scripts/check-wording.mjs` 의 `AI_TELL` · `AI_DENSE` · 문장 흐름 검사로 들였다. 출력 id 는 `[ai-…]`. 실측 결론: 우리 글은 상투구에는 거의 0 건이고, AI 같은 느낌은 **반복 · 세기 · 종결 구조** 에서 온다.

| 종류 | id | 잡는 것 → 바꿀 꼴 |
| --- | --- | --- |
| **사용자 결정** | ai-count | 세어서 끝나는 문장(«경계의 형태는 둘입니다» · «이유는 두 가지입니다») → **«~는 아래와 같습니다»** + 목록, 또는 세는 말 삭제 |
| **사용자 결정** | ai-count-dense · ai-cat-word | 세는 말(두 가지 · 둘 · 세 단계 · 첫째) 글당 6 회+ · 분류어(형태 · 종류 · 유형) 글당 4 회+ — 같은 뜻이 되풀이돼 피로하다. 개수는 표 · 목록이 보여 주게 |
| 문장 흐름 | ai-E2 · ai-chain | 같은 종결(입니다 · 했습니다 · 있습니다 …) 5 문장 연속 · «X입니다. X 는 …» 연쇄 → 합치거나 종결 바꾸기 |
| 글자 그대로 | ai-D8 · A22 · A21 · I23(밀집) | «중요한 것은» · «~은 분명합니다» · «단순한 X를 넘어» · «~다는 점입니다» 4 회+ |
| 안전망(지금 0 건) | ai-D1 ~ D14 · A8 · A19 · A23 · A24 · B2 · B4 · F1 · G2 · H4 · I7 · C6 | 결산어 · 과장어 · 의인화 · «~할 때입니다» · «~로 이어집니다» · «~하는 이유입니다» · 은유 · 이중 피동 · «~에서의» · «초석을 다지다» · «더 이상 ~않다» · 강조 부사 · 이중 완곡 · «즉» · 도입구 · 광고성 영어 |

- **넣지 않은 것**(오탐 > 30 %): «~에 있어» · «~를 바탕으로» · «~로 보입니다» · «~할 것입니다» · 연결어미 뒤 쉼표 · 같은 낱말 반복 · 문두 반복 · 제목 되풀이 · 재진술. 개발 글에서는 용어 · 주제어 반복이 정상이라 낱말 반복으로는 «같은 뜻 되풀이» 를 못 가린다.
- 이 저장소에서는 «다음과 · 아래와 같습니다» 를 잡지 않는다 — 사용자가 쓰는 말이다.
- 인용(«…» 안 · `>` 줄)은 보지 않는다. 일부러 둔 줄은 `<!-- wording-ok -->`.
- 글 레인 게이트는 `check:wording --strict` 라 `[ai-…]` 도 막는다(R-BLOG-WORDING). 고칠 때는 내용 · 숫자 · 서법(«~할 수 있다» 같은 유보)을 그대로 두고 꼴만 바꾼다.

### 사람이 읽어 보는 것 (기계로 못 잡는 AI 티)

- 두 문장이 같은 사실을 되풀이하나 → 한 문장으로. 제목 바로 아래 문장이 제목을 다시 말하나.
- «A 가 아니라 B» 대비가 몰렸나 — 판단 기준 대비(«경로가 아니라 내용»)는 정당, 수사 대비는 한 번만.
- 같은 은유가 세 번 넘게 나오나 · 인과를 «결국 ~로 이어진다» 로 건너뛰나 · «과제도 남아 있다» 뒤가 비었나.
- 모든 문단 첫 문장이 요약인가 · 문단 끝이 다 당위(«~해야 합니다»)인가 · 문장 길이가 다 비슷한가(긴 문장이 하나도 없나).
- 겪은 일 절이 처방형으로 끝나나(«~하면 됩니다» · «~세면 됩니다») → 까닭 → 결과(«~어려워, ~하게 되었습니다») · 사용자 결정 2026-11-24. 방법 · 쓰는 법 절은 그대로 둘 수 있다.
- 팀 안에서만 쓰는 말이 글에 새나 — «걸음»(단계 뜻) · 명사로 쓴 «사람 손» 은 검사가 잡는다(`[step]` · `[human-hand]` · 사용자 결정 2026-11-24). 몸 낱말 비유(손 · 발 · 눈 · 입)가 비슷하게 쓰였는지 함께 본다.
- «재다»(잰다 · 재서 · 재기 · 못 잰)가 저장소 · 코드를 대상으로 쓰였나 → «파악 · 분석»(사용자 결정 2026-11-25). 고리 끝의 «다시 재기» 는 «다시 확인». 정도 · 수치를 재는 뜻(완료를 재는 것 · 재는 자리)은 그대로 둔다 — 뜻이 갈려 기계로 못 잡는 후보라 사람이 읽는다.
- 번역투: «이루어지다» · 명사 나열 · 추상 주어 + 만능 동사(«X 가 Y 를 제공한다») · 관형절 3 겹.
- 있으면 사람 글다운 것(넣지 말고 지우지도 말 것): 필자의 자기 개입 · 당시 사정 · 힘들었던 점.

## 용어집의 결정 세 가지

| decided | 뜻 | 검사 출력 |
| --- | --- | --- |
| `user` | 사용자가 정한 말 — 대표 이름은 glossary.json 에 있다(예: 정본 → 단일 진실 원천 (SSOT), 감독 → Supervisor) | glossary 의 대표 이름을 그대로 제안 |
| `evidence` | 원천에 그 말이 거의 없고 대체어가 많이 나온다 | 바꿀 말을 제안 |
| `ask` | 원천 차이가 작거나 팀 용어다 — 바꿀지 · 무엇으로 바꿀지는 사용자가 정한다 | «(사용자 확인)» 을 붙여 후보만 |

검사는 **경고만** 낸다. 정규식은 문맥을 모른다 — 장소 뜻의 «자리», 사람에게 쓴 «키우다», «기대하다»(expect) 같은 오탐은 사람이 거른다.

## 절차

1. **검사** — `npm run check:wording [slug …]`. 줄 번호 · 규칙 id · 걸린 말 · 바꿀 말이 나온다.
2. **후보 목록** — 문맥을 보고 오탐을 뺀 뒤, 문장마다 «줄 · 지금 문장 · 바꾼 문장 · 규칙 id · 근거» 표를 만든다.
   - 바꾼 문장은 걸린 말만 바꾼다. 문장을 새로 쓰지 않는다. 조사(은/는 · 이/가 · 을/를 · 으로/로)는 바뀐 말에 맞춘다.
   - «단일 진실 원천(SSOT)» 처럼 «처음 한 번 풀어 쓰는» 말은 글마다 첫 등장에만 풀어 쓴다.
   - `ask` 항목은 바꾼 문장 대신 후보 말과 근거만 적는다.
   - 인용문: 사람이 실제로 한 말은 그대로 두고, 규칙 문서를 옮긴 인용은 결정된 용어로 바꾼다. 그대로 둔 줄은 줄 끝(또는 바로 윗줄)에 `<!-- wording-ok -->` 를 달아 검사에서 뺀다.
   - 억지 피동 · 규칙형 «~한다» 는 «선택 항목» 표로 따로 — 기본은 «그대로», 문장마다 확인받는다.
   - 글 제목이 걸리면 근거 단어로 안을 2~3개 낸다. slug 는 그대로, 시리즈 상자 · frontmatter 를 함께 고친다. 제목에서는 «처음 한 번 풀어 쓰기» 를 하지 않고 짧은 말(예: SSOT)을 쓴다 — 본문의 첫 등장에서 풀어 쓴다.
   - 같은 말이 한 글에 여러 번이면 한 줄로 묶고 줄 번호를 나열한다.
3. **사용자 확인** — 표를 보여 주고 문장마다 받는다(전부 · 일부 · 안 함). 다른 세션이 같은 글을 고치고 있으면 누가 반영할지 먼저 정한다.
4. **반영** — 확인받은 문장만 고친다. 같은 말을 글 전체에서 바꿀 때는 뜻이 같은 곳만.
5. **검증** — `npm run check:wording <slug>` 로 줄었는지, `npm run build` 통과. 커밋은 `edit:` (본문) · `chore:` (용어집 · 스킬).

## 용어집 고치기

- **용어를 바꾸거나 더할 때는 `src/data/glossary.json` 만 고친다.** 대표 이름 · 다른 이름 · 쓰지 않는 말(avoid) · 정의를 거기 한 번만 적는다. 페이지와 검사가 같은 파일을 읽으므로 문구가 두 곳에 따로 생기지 않는다.
- glossary 의 avoid 는 글자 그대로 찾는다. 활용형(키우다 → 키워 · 키운)처럼 정규식이 필요하면 `TERMS` 에 줄을 두고 `glossary: '<대표 이름>'` 으로 잇는다 — 그 줄에는 정규식만 쓴다(바꿀 말 · 결정 · 원천 근거는 glossary 에). `--list` 가 avoid 와 정규식이 어긋나면 알린다.
- 글에서는 대표 이름으로 쓴다. «대표 이름(다른 이름)» 꼴의 괄호 안(예: Supervisor(감독))은 검사가 걸지 않는다.

- 사용자가 새 말을 짚으면(«이 말 안 써»): glossary.json 에 `decided: 'user'` 로 넣고(avoid 에 그 말), 원천 실측을 세어 그 줄의 `evidence` 칸을 채운다. 원천으로 정한 말은 `kind: 'style'` · `decided: 'evidence'`.
- 실측으로 넣을 때: 안 쓰는 말과 대체어를 **같은 원천에서** 센다. 대체어가 원천에 거의 없으면 넣지 않고 `ask` 로 둔다.
- 원천은 한국어 기술 블로그 본문(회사 · 개인). 수집할 때 robots.txt 를 지키고 요청 사이를 띄운다. 문장을 옮겨 적지 않고 말의 횟수만 센다. 수집물은 저장소에 넣지 않는다.
- 이 파일 · glossary.json · `WRITING_GUIDE.md` 의 용어 절은 같은 커밋에서 고친다.

## blog-compose 와의 연결

blog-compose 의 ⑤ 초안 마무리에서 이 스킬을 돈다. 순서: **용어(이 스킬) → 윤문(humanize-korean, 선택) → SEO · GEO(blog-seo) → 초안으로 올리기**.

### 초안에서

아직 발행하지 않은 초안(`draft: true`)은 문장마다 묻지 않는다(사용자 결정 2026-11-05 — 사용자가 초안을 보고 확인한다). `decided` 가 `user` · `evidence` 인 말은 바로 고치고, `ask` 와 «선택 항목» 은 고치지 않고 초안 보고에 후보로 적는다. 숫자 · 사실 · 사람이 한 말의 인용은 그대로다. 발행한 글은 위 3~4 대로 문장마다 확인받는다.

## 하지 않는 일

- 용어집에 없는 대체어 제안, 문장 새로 쓰기
- 사용자 확인 없이 발행한 글의 본문 일괄 치환
- 숫자 · 사실 · 인용 바꾸기
- 수집한 원천 문장을 저장소 · 글에 옮기기
