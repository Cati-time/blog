# blog-seo — 검색과 AI 에 잘 전달되게

약속은 셋이다.

1. **사람에게 쓴 글이 먼저다.** 검색어를 억지로 끼우지 않는다. 제목 · 설명 · 첫 절을 «무슨 글인지 한 번에 알게» 쓰는 것이 SEO 이자 AI 전달이다.
2. **기계가 읽는 길을 모두 열어 둔다.** 사람용 HTML 말고도 원문 마크다운 · llms.txt · JSON-LD · 사이트맵 · RSS 로 같은 내용을 준다.
3. **점검은 스크립트가 한다.** `npm run check:seo` 가 오류 0 이어야 발행한다. 경고는 사람이 판단한다.

| 무엇 | 정본 |
| --- | --- |
| 점검 스크립트 | `scripts/check-seo.mjs` (`npm run check:seo` — `npm run build` 뒤) |
| 검색 메타 · JSON-LD · 원문 링크 | `src/components/BaseHead.astro` · `src/layouts/BlogPost.astro` |
| AI 용 출력 | `src/lib/llms.ts` → `/llms.txt`(목차) · `/llms-full.txt`(전 본문) · `/posts/<slug>.md`(글 원문) |
| 사이트맵 · RSS | `astro.config.mjs`(@astrojs/sitemap) · `src/pages/rss.xml.js` |
| 검색엔진 등록 · 소유 확인 | `docs/claude-management.md` §4-1 · `site.config.mjs` 의 `SEO` |
| 맨 위 주소 robots.txt | 다른 저장소 `cati-time.github.io` (블로그 세션은 읽기만 — 바꿀 일은 사용자에게 제안) |

## 글 하나를 초안으로 올리기 전에

1. **제목**: 60자 안. 무엇에 대한 글인지가 앞에 온다(예: «왜 아키텍처인가 — AI 가 코드를 쓰는 시대에»). 시리즈 번호는 뒤로.
2. **설명(description)**: 40~160자. 앞 80자에 핵심(무엇을 · 누구에게 · 무엇을 얻나). 검색 결과 · 공유 미리보기 · AI 요약에 그대로 쓰인다.
3. **«## 한 줄로» 절**: 본문 맨 앞에 결론 한두 문장. AI 답변 엔진과 검색 요약은 앞부분을 많이 쓴다.
4. **제목(h2 · h3)은 질문이나 주장으로**: «계층(layer) — 코드를 가로로 나눈다» 처럼 그 절만 읽어도 뜻이 통하게.
5. **그림 alt**: 그림이 말하는 내용을 문장으로(숫자 포함). AI 는 그림 대신 alt 를 읽는다.
6. **숫자 · 용어**: 숫자는 단위와 기준 시점까지(«규격을 정하기 직전 기준»). 용어는 용어집(`src/data/glossary.json`)의 대표 이름 — 같은 개념을 글마다 다르게 부르면 검색과 AI 가 다른 것으로 읽는다.
7. **태그 · 메뉴**: 태그는 기존 태그를 다시 쓴다. 여러 메뉴에 걸치면 `alsoIn` — 글은 하나(주소 하나)라 검색 점수가 갈리지 않는다.
8. **글 사이 링크**: 관련 글을 본문에서 잇는다. 초안으로 가는 링크는 오류(점검이 잡는다).
9. 아래 «GEO» 를 본다.
10. 초안: `npm run check:seo -- <slug>` 오류 0 · 경고 0(원문만 본다, 빌드 불필요). 발행 뒤에 나가는 빌드 결과까지는 발행할 때 `npm run build` → `npm run check:seo` 로 본다.

## GEO — AI 답변이 글을 가져다 쓰기 좋게

GEO(Generative Engine Optimization)는 ChatGPT · Perplexity · 구글 AI 요약 같은 답변 엔진이 글을 찾아 인용하기 좋게 쓰는 일이다. 이 저장소에서 효과를 잰 적은 없다. 그래서 글을 해치지 않고 사람에게도 좋은 것만 한다.

- **절이 혼자서도 뜻이 통하게**: AI 는 글 전체가 아니라 절 단위로 가져간다. 절 첫 문장을 «이것은» · «그래서» 로 시작하지 말고 주어를 쓴다.
- **용어는 처음 나올 때 한 문장으로 정의**: 팀 용어(Subflow · Business Flow …)는 특히. 정의는 용어집과 같은 문구로.
- **주장 옆에 근거**: 숫자는 기준 · 시점과 같은 문장에, 외부 인용은 출처 링크와 함께.
- **독자가 실제로 물을 말이면 질문형 소제목**: «왜 usecase 에 Repository 를 두지 않나» 처럼. 억지로 바꾸지 않고 한 글에 한두 개면 된다.
- **비교 · 절차는 표나 번호 목록으로**: 가져다 쓰기 쉽다.
- 글마다 `updatedDate` 는 내용을 고쳤을 때만 올린다. 날짜만 올려 새 글처럼 보이게 하지 않는다.

## 사이트 단위 (가끔)

- 발행 뒤 구글 Search Console · 네이버 서치어드바이저에서 새 글 «색인 요청»(사용자 계정 — 사용자가 한다).
- 빙 웹마스터 도구 등록은 아직(빙 색인은 일부 AI 검색이 쓴다) — 하려면 사용자에게 제안.
- 맨 위 주소 robots.txt 는 모든 봇 허용 + 사이트맵. AI 봇을 따로 막지 않는다(막을 때는 사용자 결정).

## 하지 않는 일

- 검색어 반복 · 숨김 글자 · 내용과 다른 설명
- 사실 확인 안 된 숫자를 설명 · 제목에 넣기
- 사용자 계정이 필요한 등록 · 제출을 대신 하기(안내만)
