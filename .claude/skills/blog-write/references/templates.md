# 글 유형별 틀

사용자의 자료에 맞는 틀을 고르고, 절 이름은 글에 맞게 바꿔도 된다. 틀은 **빈칸을 채우는 양식이 아니라 순서 안내**다. 자료가 없는 절은 지어내지 말고 `[확인 필요]` 로 묻는다.

## 1. 트러블슈팅 — "무엇이 깨졌고 어떻게 고쳤나"

대메뉴는 보통 `architecture`.

```md
## 증상        — 무엇이 어떻게 보였나 (에러 메시지, 재현 조건)
## 원인 추적   — 무엇을 의심했고 어떻게 좁혔나 (가설 → 확인)
## 원인        — 진짜 이유 한두 문단 + 핵심 코드
## 해결        — 바꾼 코드 (diff 블록 추천)
## 재발 방지   — 테스트·린트·모니터링 등
## 정리        — 같은 증상을 만난 사람을 위한 한 줄
```

## 2. 도입기·실험기 — "AI·도구를 써서 일하는 방식을 바꿨다"

대메뉴는 보통 `ax`.

```md
## 왜 시작했나  — 기존 방식의 불편 (가능하면 시간·횟수로)
## 무엇을 했나  — 도구·구성·프롬프트·워크플로 (그림이나 순서도)
## 해 보니      — 잘 된 것 / 안 된 것 / 예상 밖이었던 것
## 숫자로 보면  — 전후 비교 (없으면 이 절은 뺀다)
## 따라 하려면  — 최소 준비물과 첫걸음
## 다음         — 남은 과제
```

## 3. 설계 결정 — "왜 이 구조를 골랐나"

대메뉴는 보통 `architecture`. ADR(Architecture Decision Record) 흐름.

```md
## 맥락         — 풀어야 했던 문제와 제약
## 선택지       — 후보 2~3개 (표로 장단점 비교)
## 결정         — 무엇을 골랐나
## 이유         — 결정적인 근거
## 대가         — 포기한 것, 감수한 위험
## 지금 보면    — 결과, 다시 한다면
```

## 4. 튜토리얼·정리 — "이렇게 하면 된다"

대메뉴는 내용에 따라.

```md
## 이 글에서 할 것 — 끝나면 무엇이 되는지, 준비물
## 1단계 …        — 단계마다 코드 + 결과 확인 방법
## 2단계 …
## 자주 막히는 곳 — 에러와 해결
## 더 보기        — 공식 문서 링크
```

## 제목과 description

- 제목은 검색될 말로 구체적으로. "○○ 이야기" 보다 "○○ 에서 △△ 할 때 □□ 로 해결하기".
- description 은 **무엇을 얻을 수 있는지** 한 문장. 목록과 링크 공유 미리보기에 그대로 나온다.
