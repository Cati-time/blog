> 이 글은 [안드로이드 아키텍처 시리즈](../android-architecture-1-one-truth/) 다음 이야기입니다. 시리즈가 «도메인 상태를 한 곳에서 관리하는 구조» 를 다뤘다면, 이번에는 그 위의 **화면(UI) 계층**, 그중에서도 feature 와 feature 사이의 경계 이야기입니다.

## 한 줄로

**표준이 없으면 «다르다» 는 말할 수 있어도 «틀렸다» 는 말할 수 없습니다.** feature 사이의 경계를 두 가지 형태로 정하자, 어긋난 곳마다 «무엇을, 어느 형태로 고칠지» 가 바로 나왔습니다. 판단이 기준과 대조하는 일로 줄었습니다.

## 닫았는데 끝나지 않았다

코치마크(처음 쓰는 사람에게 화면 위에 띄우는 안내 말풍선) 작업을 Business Flow 하나로 돌렸고, 규칙 문서 기준으로 «완료» 로 닫았습니다. 남은 문제 몇 개는 «이번 범위 밖이라 미완» 으로 적어 두었습니다.

여기서 사용자의 말이 방향을 바꿨습니다.

> 고칠 수 없으니 끝이 아니라, 어떻게 하면 고칠 수 있을까다.

범위 밖이라 못 고친 것이 아니었습니다. 남은 문제를 고치려면 다른 feature 와의 경계를 건드려야 했는데, 그 경계의 형태가 feature 마다 달라서 **«어떻게 고쳐야 맞는지» 를 정할 기준이 없었습니다.**

## 다르다는 것은 셀 수 있었다

다른 feature 가 가져다 쓰는 공유 컴포넌트의 공개 인터페이스를 저장소 전체에서 세어 봤습니다. 아래 숫자는 모두 표준을 정하기 직전 시점의 저장소 기준입니다.

| 무엇 | 값 |
| --- | --- |
| 공유 컴포넌트(공개 인터페이스) | 10개 |
| 그중 `Render(modifier)` 하나만 가진 닫힌 형태 | 2개 |
| 명령형 메서드(`show()` · `dismiss()` 같은 것) | 12개 · 컴포넌트 3개에 |
| `Render` 가 아닌 화면 이름별 그리기 함수 | 10개 · 컴포넌트 4개에 |
| `Render` 에 `modifier` 말고 다른 입력을 받는 것 | 컴포넌트 4개 |

같은 «공유 컴포넌트» 인데 열 개 중 여덟 개가 서로 다른 형태였습니다. 명령형으로 띄우고 닫는 것, 화면마다 그리기 함수를 따로 둔 것, 그릴 때 이것저것 입력을 받는 것이 섞여 있었습니다.

feature 를 담는 쪽(app)도 마찬가지였습니다.

- app 이 feature 의 구현 모듈을 직접 import 하는 줄이 **122줄** 있었습니다. 공개 인터페이스(api 모듈)만 봐야 하는데 안쪽을 보고 있었습니다.
- Compose 화면 루트(`setContent` · `ComposeView`)가 있는 파일이 **app 에 14개, feature 에 60개** 흩어져 있었습니다.
- 공유 컴포넌트를 `CompositionLocal` 로 제공하는 파일도 **31개** 였습니다.

세어 보니 문제는 «나쁜 코드가 있다» 가 아니었습니다. **비교할 기준이 없다** 가 문제였습니다. 명령형 메서드를 가진 컴포넌트도 기준이 없으니 «그냥 그렇게 짠 것» 이었고, 틀렸다고 말할 근거가 없었습니다. 오히려 규칙 문서의 기준 예시가 화면 이름별 그리기 함수를 «기준» 처럼 보여 주고 있어서, 어긋난 형태가 규칙에 맞는 것처럼 읽히기도 했습니다.

## 표준을 지어내지 않고 골랐다

기준을 새로 지어내지 않았습니다. **좋은 예가 이미 코드에 있었기 때문입니다.**

- 팝업은 상태를 다루는 Host 와 상태 없이 그리기만 하는 Content 를 나눠 두었습니다.
- 팝업과 로딩, 두 컴포넌트는 이미 `Render(modifier)` 하나만 가진 닫힌 형태였습니다.
- 화면 하나를 통째로 다른 곳에 넣을 때 쓰는 `RouteEntry.Render(navigation, modifier)` 라는 꼴이 이미 규칙에 정해져 있었습니다.

앞선 리팩토링이 쌓여 나쁜 코드가 줄어들자, 좋은 예와 나쁜 예가 나란히 보이기 시작했습니다. 그래서 규칙을 «있는 것에서 골라» 정할 수 있었습니다. 대상이 정돈돼 있어서 셀 수 있었고, 세고 나서 판단했습니다.

## 경계는 두 가지 형태로만

표준은 **feature 와 feature 사이의 경계에만** 둡니다. feature 안쪽의 UI 구현은 자유입니다. 사용자는 feature 와 feature 사이의 경계에 표준이 있으면 읽기 좋다고 보았습니다.

경계의 형태는 둘입니다.

| 형태 | 언제 | 꼴 |
| --- | --- | --- |
| **삽입형** | 화면 하나를 다른 화면의 자리에 통째로 넣을 때 (Page · Slot) | `XxxRouteEntry.Render(navigation, modifier)` |
| **호출형** | 다른 feature 의 기능을 잠깐 빌려 화면 위에 띄울 때 (Overlay — 팝업 · 토스트 · 로딩) | `XxxComponent.Render(modifier)` + `dispatch(XxxRequest)` |

호출형 쪽 공개 인터페이스는 닫았습니다. **`Render(modifier)` 하나, `dispatch(request)` 하나, 그 밖에는 없습니다.** 읽기용 신호가 필요하면 그것만 선택으로 더합니다.

```kotlin
interface XxxComponent {
    @Composable
    fun Render(modifier: Modifier)          // 그리기는 한 길
    fun dispatch(request: XxxRequest)       // 요청도 한 길
}
```

여기에 세 가지 규칙이 따라옵니다.

- **보일지 말지는 module 이 판정합니다.** 몇 번 보여 줬는지, 이미 떠 있는지 같은 판정을 컴포넌트 구현이 다시 하지 않습니다.
- **쓰는 쪽은 «언제» 만 말합니다.** 화면의 ViewModel 이 자기 일회성 이벤트(sideEffect)로 시점을 알리고, Route 가 `dispatch` 를 부릅니다.
- **상태를 다루는 Host 와 상태 없는 View 를 나눕니다.** View 는 `uiState` · `event` · `modifier` 만 받습니다.

이 둘이 정해지자, 앞에서 센 «제각각» 이 전부 할 일 목록으로 바뀌었습니다. 명령형 `show()` 를 가진 컴포넌트는 «`dispatch(Request)` 로», 화면 이름별 그리기 함수는 «삽입형 Slot 으로». **판단이 기준과 대조하는 일로 줄었습니다.**

## 지킬 수 없는 규칙은 고친다

정하다 보니 원래 있던 규칙 하나가 걸렸습니다. «공유 컴포넌트는 app 에서 한 번만 제공하고, 다시 제공하지 않는다» 였습니다.

앞에서 셌듯이 Compose 화면 루트가 여러 곳에 흩어져 있습니다. `CompositionLocal` 은 루트를 넘어가지 않으니, 루트가 여럿인 지금 구조에서 «한 번만 제공» 은 지킬 수 없는 규칙이었습니다. 실제로는 루트마다 따로 제공하고 있었습니다.

루트마다 따로 제공하는 것을 예외로 허용하는 안도 있었지만 기각했습니다. 한 루트에서 컴포넌트 하나를 빠뜨려도, 기본값(`NoOp`)이 **조용히 아무것도 그리지 않기** 때문입니다. 실패 없이 기능만 사라지는, 겉만 초록인 상태가 됩니다.

그래서 규칙을 바꿨습니다. **모든 화면 루트는 app 이 가진 제공 함수 하나를 부르고, 그 밖에서는 제공하지 않습니다.** 지킬 수 없는 규칙을 그대로 두는 대신, 지킬 수 있으면서 빠뜨림이 보이는 규칙으로 고친 것입니다.

## 코치마크에 먼저 적용했다

새 표준을 처음 적용한 곳은 이야기를 시작한 코치마크입니다.

| 무엇 | 전 | 후 |
| --- | --- | --- |
| 명령형 메서드 | `show` · `dismiss` · `consume` · `setFullScreenSurfaceUp` 4개 | `dispatch(CoachmarkRequest)` 한 길 (마이그레이션용 1개만 남김 — 아래) |
| 다른 화면이 부르던 명령형 호출 | 10곳 | 0 — 모두 `dispatch` 로 |
| 그리기 | 컴포넌트의 `Render(kind, modifier)` | 앵커 자리에 삽입하는 Slot `CoachmarkAnchorRouteEntry` |
| 연결부와 View | 한 함수가 ViewModel 을 쥐고 직접 그림 | ViewModel 을 얻는 연결부(Route) → 상태 없는 `CoachmarkView` |
| 노출 판정 | 컴포넌트 구현이 «이미 떠 있나» 를 다시 판정 | module 이 판정 |

코치마크는 앱 전체에 한 번 그려지는 것이 아니라, 헤더 버튼 위 · 하트 아래 · 플로팅 버튼 위처럼 **쓰는 화면 안의 정해진 곳** 에 그려집니다. 그래서 «호출형» 의 `Render` 로 그리지 않고, 요청은 `dispatch` 로 받되 그림은 앵커 자리에 삽입하는 Slot 으로 나눴습니다. 표준에 딱 맞는 꼴이 없어 규칙을 관리하는 쪽에 판정을 받은 뒤 정했습니다.

리팩토링이라 동작은 바뀌면 안 됩니다. 처음에 만든 골든마스터 테스트(세 종류 말풍선의 문구 · 노출 · 숨김 · 소진 · 덮임)의 **단언은 그대로 두고**, 바뀐 구조에 맞춰 테스트를 구동하는 부분만 고쳤습니다.

## 무엇과 언제를 가르면 계획이 쉬워진다

걸림돌이 하나 있었습니다. 앱의 홈 화면은 다른 큰 작업이 진행 중이라 이번에는 건드리면 안 되는 상태였는데, 홈 화면이 바로 이 명령형 메서드 중 하나(`setFullScreenSurfaceUp`)를 부르고 있었습니다.

**무엇을 할지** 와 **언제 할지** 를 나눠 보니 일 전체를 미룰 필요가 없었습니다. 그 메서드 하나만 «마이그레이션용» 으로 남기고 안에서 `dispatch` 로 넘기게 한 뒤, 홈 화면을 건드리는 일은 마지막 조각 하나로 모았습니다. 조각 수는 늘었지만, 조각이 늘어나는 것은 괜찮다는 것이 사용자의 판단이었습니다. 막힌 것은 일 전체가 아니라 마지막 조각 하나였습니다.

## 인터페이스가 판단을 코드로 옮긴다 — 다음 단계

솔직히 적으면, 지금 이 표준은 **규칙 문서에 적힌 규칙** 입니다. 지키는지는 리뷰와 명령으로 다시 세어 확인합니다. 코치마크도 «명령형 호출 0» 을 검사 테스트가 아니라 다시 세어서 확인했습니다. 호출형 쪽 형태를 지켜보는 가드는 아직 없습니다.

이번 일에서 얻은 깨우침 하나가 다음 단계를 정했습니다. 규칙 문서와 가드는 읽고 지켜야 하는 것이라, 이번처럼 «완료지만 구조는 아님» 같은 틈이 생깁니다. 표준을 **타입** 으로 박으면 어긋난 형태는 컴파일부터 되지 않습니다. 규칙이 «기억할 것» 에서 «어길 수 없는 것» 이 됩니다.

그래서 다음 단계로 정해 둔 것은 이렇습니다.

- 공유 View · ViewModel 의 공통 타입을 core 에 둔다.
- 타입으로 못 막는 셋만 검사로 막는다. ViewModel 은 Route · Host 에서만 얻는다, 맨 위 View 는 상태가 없다, 제공은 제공 함수 안에서만 한다.

남은 마이그레이션도 숨기지 않고 적어 둡니다. app 이 feature 구현을 직접 import 하는 122줄과 feature 구현끼리 옆으로 의존하는 곳을 공개 인터페이스로 돌리고, 화면 루트마다 제공 함수를 부르게 바꾸는 일이 남아 있습니다. 토스트 · 로딩 같은 다른 공유 컴포넌트도 차례로 같은 형태로 옮깁니다.

## 정리

- **기준이 생기니 «다르다» 가 «무엇을 고칠지» 로 바뀝니다.** 표준이 없을 때는 틀렸다고 말할 근거가 없었습니다.
- **표준은 feature 사이의 경계에만, 형태는 둘만.** 삽입형(`RouteEntry`)과 호출형(`Component` + `dispatch`). 안쪽은 자유입니다.
- **지킬 수 없는 규칙은 고칩니다.** 빠뜨려도 조용히 지나가는 예외보다, 빠뜨림이 보이는 규칙이 낫습니다.
- **리팩토링이 쌓여야 구조가 보입니다.** 나쁜 코드가 줄자 좋은 예를 골라 규칙으로 정할 수 있었습니다. 다음은 그 규칙을 타입으로 옮기는 일입니다.
