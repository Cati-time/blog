> 이 글은 [안드로이드 아키텍처 시리즈](../android-architecture-1-one-truth/) 다음 이야기입니다. 시리즈가 «도메인 상태를 한 곳에서 관리하는 구조» 를 다뤘다면, 이번에는 그 위의 **화면(UI) 계층** 이야기입니다.

## 한 줄로

**규격이 없으면 «다르다» 는 말할 수 있어도 «틀렸다» 는 말할 수 없습니다.** feature 와 feature 가 만나는 곳에 규격을 두 가지 모양으로 정하자, 어긋난 곳마다 «무엇을, 어느 모양으로 고칠지» 가 바로 나왔습니다. 그리고 그 규격을 타입으로 박자, 규칙은 «기억할 것» 에서 «어길 수 없는 것» 이 됐습니다.

## 닫았는데 끝나지 않았다

코치마크(처음 쓰는 사람에게 화면 위에 띄우는 안내) 작업을 Business Flow 하나로 돌렸고, 규칙 문서 기준으로 «완료» 로 닫았습니다. 남은 문제 넷은 «이번 범위 밖이라 미완» 으로 적어 두었습니다.

여기서 사용자의 말이 방향을 바꿨습니다. «고칠 수 없으니 끝이 아니라, 어떻게 하면 고칠 수 있을까다. 코드 구조가 나쁘고 규칙이 안 지켜져서다.»

범위 밖이라 못 고친 것이 아니었습니다. 고치려면 다른 feature 와 만나는 곳을 건드려야 했는데, 그 만나는 곳의 모양이 화면마다 달라서 «어떻게 고쳐야 맞는지» 를 정할 기준이 없었습니다.

## 다르다는 것은 셀 수 있었다

같은 «화면 계층의 인터페이스» 를 저장소 전체에서 세어 봤습니다. <!-- 숫자: 사실 확인 뒤 원천 값으로 채움 -->

- **공유 컴포넌트가 밖으로 내놓는 모양이 전부 달랐습니다.** 그리기 함수만 있는 것, 명령형 `show()` · `dismiss()` 를 가진 것, 화면 이름마다 그리기 함수를 따로 둔 것, ViewModel 을 그대로 내놓는 것이 섞여 있었습니다.
- **화면을 그리는 대표 함수의 모양도 여러 가지였습니다.** `(state, onEvent)` 두 개만 받는 것은 소수였고, 상태에 콜백을 낱개로 여러 개 받는 것, 인자를 낱개로 받는 것이 대부분이었습니다.
- **app 모듈이 feature 내부를 직접 import 하는 곳**, feature 구현끼리 옆으로 의존하는 곳이 있었습니다. Compose 의 화면 루트도 app 과 feature 양쪽에 흩어져 있어서, «한 곳에서 한 번 제공한다» 가 불가능했습니다.

세어 보니 문제는 «나쁜 코드가 있다» 가 아니었습니다. **비교할 기준이 없다** 가 문제였습니다. 명령형 메서드를 가진 컴포넌트도, 기준이 없으니 «그냥 그렇게 짠 것» 이었고 틀렸다고 말할 근거가 없었습니다.

## 규격을 지어내지 않고 골랐다

기준을 새로 지어내지 않았습니다. **좋은 예가 이미 코드에 있었기 때문입니다.**

- 팝업은 화면 위에 띄울 자리(Host)와 그 안의 내용(HostContent)을 나눠 두었습니다.
- 맞춤 편지 화면은 View 가 `(state, onEvent)` 두 개만 받았습니다.

앞선 리팩토링이 쌓여 나쁜 코드가 줄어들자, 좋은 예와 나쁜 예가 나란히 보이기 시작했습니다. 그래서 규칙을 «있는 것에서 골라» 정할 수 있었습니다. 대상이 정돈돼 있어서 셀 수 있었고, 세고 나서 판단했습니다.

## 만나는 곳은 두 가지 모양으로만

규격은 **feature 와 feature 가 만나는 곳에만** 둡니다. feature 안쪽의 UI 는 자유입니다. 사용자 말로는 «feature 와 feature 가 결합될 때 규격이 있으면 읽기 좋다» 입니다.

만나는 모양은 둘로 정했습니다.

| 모양 | 언제 | 꼴 |
| --- | --- | --- |
| **끼워 넣기** | 화면 하나를 통째로 다른 곳(내비게이션)에 넣을 때 | `RouteEntry.Render(navigation, modifier)` |
| **불러 쓰기** | 다른 feature 의 기능(팝업 · 코치마크 등)을 잠깐 빌려 쓸 때 | `Component.Render()` + `dispatch(Request)` |

이 둘이 정해지자, 앞에서 센 «제각각» 이 전부 할 일 목록으로 바뀌었습니다. 명령형 `show()` 를 가진 컴포넌트는 «불러 쓰기 모양으로, `dispatch(Request)` 로», 화면 이름마다 그리기 함수를 둔 것은 «끼워 넣기 모양으로, `RouteEntry` 하나로». **판단이 기준과 대조하는 일로 줄었습니다.**

## 인터페이스가 판단을 코드로 옮긴다

규격을 규칙 문서에 적고 가드로 검사할 수도 있었습니다. 하지만 문서와 가드는 읽고 지켜야 하는 것이라, 이번처럼 «완료지만 구조는 아님» 같은 틈이 생깁니다.

그래서 규격을 **타입** 으로 박았습니다. `UiViewModel` · `UiView` 같은 인터페이스와, 만나는 곳에 넘기는 값의 타입을 정해 두면, 어긋난 모양은 **컴파일부터 되지 않습니다.**

- 규칙이 «기억할 것» 에서 «어길 수 없는 것» 이 됩니다.
- 가드로 남는 것은 타입으로 막을 수 없는 몇 가지뿐입니다. 신경 쓸 범위가 좁아집니다.

## 무엇과 언제를 가르면 계획이 쉬워진다

옮기는 계획에도 걸림돌이 하나 있었습니다. 앱의 홈 화면은 분석 이벤트 전환 작업이 끝나기 전까지 건드리면 안 되는 상태였습니다. 처음에는 이것 때문에 일 전체를 미뤄야 하는 줄 알았습니다.

**무엇을 할지** 와 **언제 할지** 를 나눠 보니 달랐습니다. 홈 화면을 건드리는 일은 마지막 조각 하나로 모으고, 나머지 조각을 먼저 하면 됐습니다. 조각 수는 늘었지만, 사용자 말대로 «슬라이스가 늘어나는 건 문제가 아니다» 였습니다. 막힌 것은 일 전체가 아니라 마지막 조각 하나였습니다.

## 검증도 구조가 쉽게 만든다

리팩토링은 «화면이 안 바뀌었다» 를 증명해야 합니다. 상태가 없는 View 는 이 증명이 쉽습니다. `uiState` 만 넣으면 같은 화면이 그려지니, 스크린샷 테스트(Roborazzi)로 바꾸기 전과 후의 이미지를 비교하면 됩니다. 단, 비교할 기준 이미지는 **첫 커밋 전에** 찍어 둬야 합니다.

구조를 바로잡으니 검증까지 쉬워졌습니다. 반대로 말하면, 상태를 품은 View 는 이 검증부터 어렵습니다.

## 정리

- **기준이 생기니 «다르다» 가 «무엇을 고칠지» 로 바뀝니다.** 규격이 없을 때는 틀렸다고 말할 근거가 없었습니다.
- **인터페이스가 판단을 코드로 옮깁니다.** 타입으로 박은 규칙은 어길 수 없고, 남는 가드가 줄어듭니다.
- **리팩토링이 쌓여야 구조가 보입니다.** 나쁜 코드가 줄자 좋은 예를 골라 규칙으로 정할 수 있었습니다.

규격은 feature 가 만나는 곳에만 둡니다. 안쪽까지 규격으로 묶지 않은 것이, 이 규격을 받아들이기 쉽게 만든 이유이기도 합니다.
