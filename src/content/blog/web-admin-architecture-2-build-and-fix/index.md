> **웹 어드민 아키텍처 시리즈**
> [① 지금의 구조 — 계층마다 모르는 것](../web-admin-architecture-1-structure/) · ② 새로 만들고 고치기 (이 글) · [③ 어떻게 옮겨 왔나](../web-admin-architecture-3-how-we-moved/)

## 한 줄로

**새 기능은 «어느 계층에 무엇을 넣나» 가 정해져 있어서, 바뀌는 곳이 작고 예측됩니다.** 화면을 지울 때도 가드가 «이 삭제가 어디까지 번지는지» 를 알려 줍니다.

[앞 편](../web-admin-architecture-1-structure/) 에서 네 계층과 각자 모르는 것을 봤습니다. 이번에는 실제 작업 두 건을 계층별로 따라갑니다.

## 사례 1 — 쓰기 버튼을 권한으로 숨기기

### 문제

화면은 열 수 있는데 쓰기 권한이 없는 역할이 있습니다. 그런 사람이 쓰기 버튼을 누르면 서버가 403 을 돌려줍니다. 버튼이 보이는데 누르면 실패하는 셈입니다. 역할별 메뉴를 정리하면서 감사가 이 빈틈을 찾았는데, 그것을 잡는 검사가 없었습니다.

### 먼저 검사부터

이 작업은 화면을 고치기 전에 **검사부터** 세웠습니다. «숨긴 쓰기 목록» 을 기준으로, 화면마다 어떤 쓰기를 숨겼는지 검사합니다. 이때 쓰기 요청의 메서드 · 경로 · 허용 역할은 사람이 목록에 손으로 적지 않고, 검사가 코드와 게이트웨이 규칙 사본에서 직접 뽑습니다. 손으로 적은 값은 언젠가 틀리기 때문입니다.

그다음 화면을 하나씩 고쳤습니다. 모두 11개 화면입니다.

### 어느 계층에 무엇을 넣었나

관리자 사용자 화면을 예로 들면, 바뀐 곳은 이렇습니다.

| 계층 | 한 일 |
| --- | --- |
| module/auth · 메뉴 트리 | 권한 카탈로그에 이미 있던 키 `'admin-user:write': ['ADMIN']` 를 메뉴 트리의 `writePermissions` 한 칸에 연결 |
| feature (ViewModel 옆) | 훅 하나, 본문 두 줄: `snapshot.can('admin-user:write')` 를 돌려줌 |
| feature (ViewModel) | 그 값을 `canWrite` 한 칸으로 내려보냄(이 화면은 아직 uiState 꼴이 아니라 ViewModel 반환값). 쓰기 핸들러 첫 줄에 `if (!canWrite) return;` |
| feature (View) | `canWrite` 가 거짓이면 버튼을 **아예 그리지 않음**(disabled 로 두지 않음) |
| 검사 | 화면별 쓰기 숨김 검사 + 전체 목록 검사 |

이 작업이 새로 만든 «쓰기 권한 훅» 이 11개이고, 전부터 있던 것까지 지금 12개입니다. 모양이 전부 같습니다.

### 규칙이 실제로 한 일

이 작업에서 앞 편의 규칙 두 개가 실제로 판정을 모아 줬습니다.

- **View 는 Store 를 부를 수 없습니다.** 그래서 «이 사람이 쓸 수 있나» 의 판정이 ViewModel 한 곳에만 생깁니다. 화면 여기저기에 같은 판정이 흩어지지 않습니다.
- **feature 는 역할 이름을 쓸 수 없습니다.** 화면은 `ADMIN` 이 아니라 권한 키로만 묻습니다. 이 규칙에는 계기가 있습니다. 화면 밖에서 역할 목록을 다시 적었더니 게이트웨이에 없는 역할이 되살아나고 실제 있는 역할이 빠진 일이 있었습니다. 역할 선택지와 라벨 표가 두 벌로 그 상태였습니다.

## 사례 2 — 화면 하나 제거하기

### 결정

대화 기록 화면 하나를 없애기로 했습니다. 사용자 결정은 «없애자» · «잃어도 됨» 이었습니다. 그 화면을 쓰던 CS 담당자를 위해서는 비슷한 다른 화면(User Tracking)에 권한을 새로 열었고, 옛 주소로 들어오면 새 화면으로 보냅니다(북마크 보존).

### 어느 계층에서 무엇이 같이 움직였나

- **feature** — 화면 폴더를 통째로 지우고, 라우터와 메뉴 트리에서 뺐습니다.
- **module** — 그 화면의 module 을 통째로 지웠습니다(store · actions · atoms · service).
- **data** — 목록 API 호출과 DTO 를 지웠습니다. 단, **녹음 파일 주소를 가져오는 호출은 남겼습니다.** User Tracking 이 그것을 재사용하기 때문입니다. 새 클라이언트를 만들지 않고 있는 것을 씁니다.
- **module/auth** — 권한 키를 지우고 새 키를 만들었습니다.

### 가드가 «어디까지 번지나» 를 알려 줬다

지우는 커밋 안에서 **예외 목록(worklist)과 그 상한 값을 같이 내렸습니다.** 지운 ViewModel 이 «아직 고치지 못한 예외» 목록에 있었으니 그 줄을 빼고, 목록 길이의 상한도 32 에서 31 로 내렸습니다. 상한은 «이하» 로 비교해서 안 내려도 테스트는 초록입니다. 그래도 같은 커밋에서 사람이 내립니다. 예외 목록은 늘릴 수 없고 줄어들기만 하게 해 두었기 때문입니다.

그리고 **다른 검사 두 개가 따로 빨개졌습니다.** 하나는 쓰기 숨김 목록에 지운 화면의 줄이 남아 있었고, 다른 하나는 다른 기능의 사실 검사가 «module 은 71개» 를 고정해 두고 있었습니다. 둘 다 후속 커밋으로 고쳤습니다(module 71 → 70).

좋은 점과 비용이 같이 보입니다. 지울 때도 가드가 일해서 놓친 곳이 남지 않았습니다. 대신 화면 하나와 상관없어 보이는 검사에도 값이 고정되어 있어서, 한 번 더 고쳐야 했습니다.

## 규칙과 가드가 실제로 잡은 것

두 사례 말고도, 규칙이나 가드가 실제로 문제를 잡은 기록이 몇 개 있습니다.

**ESLint override 가 규칙을 조용히 꺼 버렸다.** ESLint 의 override 는 같은 규칙을 합치지 않고 **바꿔치기** 합니다. 토큰 저장소 규칙을 최상위에만 뒀더니, feature 와 module 의 override 가 그것을 덮어 써서 그 구역에서 규칙이 꺼져 있었습니다. 지금은 그 규칙을 상수로 빼서, 각 구역에서 마지막으로 걸리는 override 가 그 상수를 참조합니다.

**규칙 문장을 그대로 재 보니 오탐이 났다.** «module 에서 React import 는 0» 이라는 규칙을 글자 그대로 재니 오탐이 167건 나왔습니다(결정 기록에 남은 값입니다). module 의 Store 는 Recoil 훅이라 `useMemo` 같은 것을 정당하게 import 하기 때문입니다. 그래서 금지 대상을 «React 렌더(JSX)» 로 좁혔습니다. 규칙 문서의 문장도 재 보고 고칩니다.

**테스트 60개가 넘게 초록인데 기능은 2주 가까이 안 됐다.** 콘텐츠 생성 엑셀 내려받기가 2주 가까이(13일) 한 번도 성공하지 못했습니다. 연동 테스트은 모두 초록이었지만, `window.open` 은 Origin 헤더를 보내지 않아서 데몬이 거절하고 있었습니다. 테스트가 문서와 다른 것을 재고 있었고, 그 자리를 재는 테스트는 없었습니다. 고칠 때는 계층을 그대로 따랐습니다. data 가 받아 오고, module 이 내보내고, feature 가 파일로 만들어 내려받게 했습니다.

**검사가 «본 척» 하던 자리.** 검사 자체에도 허점이 있었습니다. 검사가 실제로는 대상을 하나도 보지 않았는데 통과로 끝나는 경우입니다. 그래서 새 검사는 모두 **몇 개를 봤는지 출력하고, 0개를 봤으면 실패** 해야 한다고 규칙으로 정했습니다. 지금 본 개수를 출력하는 테스트 파일은 전체 511개 중 116개입니다.

## 정리

- 새 기능은 계층마다 넣을 곳이 정해져 있습니다. 권한 하나를 더해도 module 에 키 하나, ViewModel 에 훅 하나, View 에 조건 하나입니다.
- 지울 때도 가드가 «어디까지 번지는지» 를 알려 줍니다. 대신 상관없어 보이는 곳에 고정된 값이 있으면 한 번 더 고쳐야 합니다.
- 테스트가 초록이어도, **그 자리를 재는 테스트가 없으면** 기능은 깨져 있을 수 있습니다.
