## 한 줄로

**웹 어드민은 네 계층(app → feature → module → data)으로 나뉘고, 각 계층이 무엇을 모르는지를 규칙으로 정해 둡니다.** 상태는 «화면이 없어도 존재하는가» 를 기준으로 세 단계에 나눠 둡니다.

웹 어드민은 운영자 · CS · 콘텐츠 담당자가 쓰는 사내 운영 도구입니다. React · TypeScript · Recoil 로 만들었고, 화면이 수십 개입니다. 시리즈는 세 편입니다. 이 글은 지금의 구조와 그 이유를, [②편](../web-admin-architecture-2-build-and-fix/) 은 이 구조로 실제 기능을 만들고 고친 사례를, [③편](../web-admin-architecture-3-how-we-moved/) 은 1년 전 구조에서 여기까지 옮겨 온 길을 다룹니다.

## 네 계층과 각자 모르는 것

![웹 어드민 구조. app 이 feature 의 Entry 를 마운트하고, feature 안에는 Entry · View · ViewModel 이 있다. 휘발 상태는 View 의 useState, 화면 지속 상태는 uiAtoms 에 둔다. Store 는 ViewModel 만 부르고 state · actions · snapshot 을 받는다. module 은 도메인 상태(SSOT)를 관리하며 actions 가 service 를 불러 결과를 atoms 에 저장한다. data 는 REST 호출 · DTO 만 하고, 권한은 게이트웨이 · 서버가 강제한다. core(useApiQuery · antd 파사드)는 계층 밖에서 가로지른다](./architecture.svg)

| 계층 | 하는 일 | 모르는 것 |
| --- | --- | --- |
| **app** | 진입 · 라우트 · 내비게이션. 화면의 Entry 를 마운트만 한다 | module 도 data 도 모른다 |
| **feature** | 화면. Entry(생명주기) · View(순수 렌더) · ViewModel(상태 · 이벤트) | data 를 모른다. module 내부 파일을 모른다. 역할 이름(`ADMIN` 등)을 모른다 |
| **module** | 도메인 상태와 동작. 밖으로는 `use<이름>Store()` 하나로 `{ state, actions, snapshot }` 만 내놓는다 | React 렌더 · 라우터 · feature 를 모른다 |
| **data** | I/O 전용. REST 호출 · DTO · 직렬화 | feature · app 의 타입과 훅을 모른다 |

여기에 계층이 아닌 **core** 가 있습니다. 여러 계층이 같이 쓰는 공통 코드입니다. core 에 있는 파일이 어느 계층 몫인지는 경로가 아니라 내용으로 정합니다. I/O 를 하면 data 몫이고, 안 하면 공통입니다.

feature 안에서도 더 나눕니다. **View 는 module 의 값을 모르고(타입만 압니다), Store 를 부를 수 있는 곳은 ViewModel 하나** 입니다. 그래서 화면에서 무엇을 판정하든 그 판정은 ViewModel 한 곳에 모입니다.

왜 «모르는 것» 으로 정할까요. 안드로이드 편에서 쓴 것과 같은 이유입니다. 아는 것이 늘면 바꿀 때 같이 고쳐야 할 곳이 늘어납니다. 모르는 것을 정해 두면, 바꿀 때 영향이 그 계층 안에서 멈춥니다. 특히 이 저장소는 AI 에이전트가 코드를 많이 씁니다. 사람이 «알아서 조심하겠지» 를 기대할 수 없는 곳은 규칙으로 막아 둬야 합니다.

## 상태는 세 단계에 둔다

상태를 어디에 둘지는 질문 하나로 정합니다. **«아무도 이 화면을 보고 있지 않아도, 이 상태가 존재해야 하는가?»**

| 단계 | 기준 | 어디에 | 예 |
| --- | --- | --- | --- |
| 도메인 | 화면 수명과 무관하다 | module 의 Recoil atom | 선택된 회사, 로그인 세션, 서버에서 받은 목록 |
| 화면 지속 | 화면을 떠났다 돌아와도 남아야 한다 | feature 의 `uiAtoms.ts` | 페이지 번호, 정렬, 검색 필터, 탭 |
| 휘발 | 화면을 다시 그리면 사라져야 한다 | `useState` (View 또는 ViewModel 안) | 포커스, 스크롤, 펼침 |

이 기준에서 나온 규칙이 하나 있습니다. **로딩 · 에러는 module 상태가 아닙니다.** 세션이 확립되는 중이라는 사실은 아무도 화면을 안 봐도 존재하니 도메인입니다. 하지만 `isLoading` 은 «누군가 기다리고 있다» 는 뜻일 뿐이라 화면 상태입니다. 도착하기 전의 데이터는 «로딩 값» 이 아니라 그냥 **빈 값** 입니다.

한 질문에는 답하는 곳을 하나만 둡니다. 화면이 «이 사람이 이 버튼을 눌러도 되나» 를 알고 싶으면, 원본 필드를 가져와 직접 비교하지 않고 `snapshot.can(권한)` 하나를 읽습니다. 단일 진실 원천(SSOT)을 상태 수준에서 지키는 방법입니다.

## 화면 하나를 끝까지 — User Tracking

실제 화면 하나를 라우트부터 API 까지 따라가 보겠습니다.

1. **라우트** — 경로에 권한 키를 건 게이트를 씌웁니다. 권한이 없으면 화면 대신 «권한 없음» 이 나옵니다.
2. **Entry** — ViewModel 을 부르고, 마운트 · 언마운트 이벤트만 보냅니다. 렌더는 View 에게 넘깁니다. `useEffect` 는 Entry 에만 있습니다. ViewModel 에서는 규칙으로 막혀 있습니다.
3. **View** — 받는 것은 `uiState` 와 `event` 둘뿐입니다. 받은 상태를 나눠 그릴 뿐, 조합해서 판단하지 않습니다.
4. **ViewModel** — 여기서 세 단계 상태가 한눈에 보입니다. 조회 결과는 module 의 Store(도메인), 검색 입력과 페이지는 `uiAtoms`(화면 지속), `isLoading` 은 `useState`(휘발)입니다. 권한은 `snapshot.can(...)` 으로 묻습니다. 화면 입력을 도메인 조회 조건으로 바꿔 module 의 action 을 부릅니다.
5. **module** — action 이 조회 조건을 먼저 저장하고, service 를 불러 결과를 저장합니다. 실패하면 직전 목록을 유지합니다. service 는 data 의 API 훅을 감싼 얇은 래퍼이고, HTTP 클라이언트가 무엇인지 모릅니다.
6. **data** — 쿼리 파라미터를 조립해 API 를 부릅니다.

계약 문서도 코드 옆에 같이 있습니다. feature 폴더에는 API · BDD · SDD 문서가, module 폴더에는 상태 계약서(`STATE.md`)가 있습니다. module 70개 중 45개가 상태 계약서를 갖고 있습니다.

## 웹이라서 내린 결정

### 서버 상태 라이브러리를 쓰지 않는다

이 저장소에는 react-query · SWR · axios 가 없습니다. 관리 서버(REST) 호출은 직접 만든 `useApiQuery` 훅이 맡습니다. 로컬 데몬 · 외부 TTS 업체 · 미디어 파일 내려받기는 data 계층이 `fetch` 를 직접 쓰고, 로그인만 아직 옛 네트워크 유틸을 씁니다. 토큰을 붙이고, 401 과 403 을 한 곳에서 처리합니다.

- **401** 은 세션 만료로 보고 로그아웃합니다.
- **403** 은 로그아웃하지 않습니다. 권한이 없다는 오류만 보여 줍니다.

캐시 키나 무효화 계층이 따로 없는 대신 규칙이 하나 있습니다. **변경 action 은 반환하기 전에 필요한 재조회까지 끝낸다.** 화면이 `actions.a()` 다음에 `actions.b()` 를 직접 엮는 것은 금지입니다. 이 규칙이 왜 이렇게 엄격한지는 사용자의 말이 결정 기록에 남아 있습니다. «액션 없이 state 를 바꾸려고 한다든가, view 에서 조합해서 쓴다든가. 그런 행동을 너는 잘하더라고.» AI 에이전트가 자주 하는 실수를 구조로 막은 것입니다.

### 권한은 서버가 강제하고, 웹은 같은 답으로 화면만 가린다

권한을 실제로 막는 것은 서버(게이트웨이)입니다. 웹은 같은 답을 내서 메뉴와 버튼을 가릴 뿐입니다. 문제는 웹이 그 답을 알려면 서버 규칙의 사본을 가져야 한다는 점입니다. 사본은 서버가 바뀌면 **말없이 낡습니다.**

그래서 사본을 세 벌로 두고, 시험으로 서로 대조합니다.

1. **권한 카탈로그** — 권한 키마다 허용 역할. 키와 역할의 모든 조합을 시험이 고정합니다.
2. **게이트웨이 대표 규칙 사본** — 키마다 게이트웨이 규칙 한 줄. 어느 게이트웨이 커밋에서 옮겼는지를 같이 적어 두고, 화면 범례에도 보여 줍니다.
3. **경로 단위 체인 사본** — 같은 화면 안에서도 경로마다 판정이 갈리는 경우를 위해, 게이트웨이의 경로 규칙을 줄 단위로 옮겨 둡니다.

다른 저장소라 CI 가 자동으로 대조하지 못한다는 한계는 사본 파일 머리에 그대로 적어 두었습니다. 그리고 **모르는 역할은 «권한 없음» 으로** 처리합니다. «모르니까 통과» 는 절대 안 됩니다.

### 엑셀은 세 가지 길

운영 도구라 엑셀이 많습니다. 같은 «엑셀» 이어도 바이트를 누가 만지느냐에 따라 길을 셋으로 나눴습니다.

| 용도 | 어디서 |
| --- | --- |
| 질문 가져오기 · 내보내기 | 브라우저에서 파싱 · 생성 (feature 안 두 파일) |
| 인텐트 엑셀 업로드 | 브라우저는 파일을 보내기만, **검증은 서버** |
| 콘텐츠 생성 엑셀 | 로컬 에이전트 데몬이 만들고, 웹은 내려받기만 |

### ESLint 는 경고만, 막는 것은 빌드

ESLint 는 경고만 내도록 돌립니다. 실제로 막는 것은 `CI=true npm run build` 입니다. 빌드가 경고를 에러로 올립니다. 테스트 파일은 빌드가 보지 않아 ESLint 로 막을 수 없으니, 그쪽 규칙은 테스트로 막습니다.

솔직히 적어 두면, **기계가 막는 범위는 생각보다 좁습니다.** 상태를 세 단계 중 어디에 둘지, 판정을 화면에서 다시 하지 않는지 같은 규칙은 정적으로 판정할 수 없어서 사람이 리뷰로 지킵니다.

## 정리

- 네 계층(app → feature → module → data)은 **각자 모르는 것** 으로 나뉩니다.
- 상태는 «화면이 없어도 존재하는가» 로 도메인 · 화면 지속 · 휘발 세 단계에 둡니다. 로딩은 도메인 상태가 아닙니다.
- 서버 상태 라이브러리 없이 `useApiQuery` 하나와 «변경 action 이 재조회까지 끝낸다» 는 규칙으로 갑니다.
- 권한의 강제는 서버, 웹은 사본으로 화면만 가리고, 사본은 시험으로 대조합니다.

다음 편에서는 이 구조로 실제 기능을 만들고, 화면 하나를 걷어 낸 사례를 봅니다.
