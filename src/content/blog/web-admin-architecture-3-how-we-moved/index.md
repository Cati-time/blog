> **웹 어드민 아키텍처 시리즈**
> [① 지금의 구조 — 계층마다 모르는 것](../web-admin-architecture-1-structure/) · [② 새로 만들고 고치기](../web-admin-architecture-2-build-and-fix/) · ③ 어떻게 옮겨 왔나 (이 글)

## 한 줄로

**한 번에 갈아엎지 않고, 기능 하나를 Business Flow 하나로 잡아 조각 단위로 옮겼습니다.** 지금도 옮기는 중이고, 줄지 않은 것도 있습니다.

## 1년 전 — 로직은 `component/` 에 몰려 있었다

1년 전 코드에는 지금의 계층이 없었습니다. module 도, 화면 Entry 도, 상태 계약서도, 규칙 문서도 없었고 테스트 파일은 1개였습니다.

로직이 몰려 있던 곳은 `src/component/` 아래 203개 파일이었습니다. 흔히 «유틸 폴더에 다 몰려 있었다» 고 기억하기 쉬운데, 실제 유틸 폴더는 4개 파일뿐이었습니다. 호출 모양은 이랬습니다. 도메인마다 `fetch/` 폴더의 파일이 공용 네트워크 유틸을 직접 불러 응답을 돌려주고, 페이지 컴포넌트가 그것을 받아 상태를 만졌습니다. 그런 fetch 파일이 31개였고, 31개 모두 네트워크 유틸을 직접 썼습니다.

거대 파일도 있었습니다. 인텐트 상세 화면 하나가 1,800줄이 넘었고, 그 옆의 응답 편집 화면도 1,700줄이 넘었습니다. Recoil 은 이미 쓰고 있었지만, 첫 설계 문서의 진단대로 atom · 명령형 API 호출 · 파생 상태가 기능 폴더마다 흩어져 있었습니다.

## 어떻게 옮겼나 — 기능 하나 = Business Flow 하나

### 단위

옮기는 단위는 **기능 하나(또는 module 하나)** 입니다. 그것을 Business Flow 하나로 잡고, 다시 조각(S0, S1 …)으로 나눠 하나씩 옮깁니다. 커밋 제목이 `refactor(<기능>/S3): …` 꼴입니다. 마지막 조각은 언제나 «옛 표면 제거» 입니다. 새 구조로 다 옮긴 뒤에야 옛 코드를 지웁니다.

### 순서

1. **처음** — `view · viewModel · store` 꼴과 `useApiQuery`, data 의 API 훅 구조는 이보다 훨씬 전에 이미 생겨 있었습니다. 문제는 그것이 일부에만 쓰였다는 점입니다.
2. **그다음** — 인증과 한 기능에 module 의 `{ state, actions }` 계약을 처음 적용했습니다. 안드로이드에서 쓰던 규칙을 웹으로 옮겨 와 첫 시범으로 앱 버전 화면에 적용했습니다.
3. **규칙 문서가 생긴 뒤** — 규칙 문서를 따로 두고, 그 뒤로 기능마다 Business Flow 를 돌렸습니다. 공용 네트워크 유틸 호출을 `useApiQuery` 로 옮기는 일, 인증 토큰 저장소를 module 하나가 맡게 하는 일, 상태를 세 단계로 나누는 규칙이 이때 들어왔습니다.
4. **지금** — feature 가 data 를 직접 부르지 못하게 하는 규칙을 ESLint 로 켰고, 역할별 메뉴, 쓰기 버튼 가림처럼 화면 전체에 걸친 일을 했습니다.

규칙 문서가 생긴 뒤로 커밋 밀도가 크게 달라졌습니다. 다만 이것을 «이행이 빨라졌다» 로 읽으면 틀립니다. 그 무렵부터 사람과 AI 에이전트(Supervisor · Business Flow 를 실행하는 세션)가 병렬로 일하기 시작했습니다. 일하는 방식이 바뀐 것입니다.

## 처음과 지금 — 같은 기준으로 센 숫자

1년 전 코드와 지금 코드를 같은 기준으로 셌습니다.

| 무엇 | 1년 전 | 지금 |
| --- | --- | --- |
| `src/component/` 파일 | 203 | **2** |
| 공용 네트워크 유틸을 직접 쓰는 소스 | 35 | **1** |
| module (Store 가 있는 곳) | 0 | **70** |
| 화면 Entry | 0 | **68** |
| ViewModel 파일 | 31 | 119 |
| 테스트 파일 | 1 | **511** |

feature 가 data 를 직접 부르는 예외는 규칙을 켠 날 168개 파일이 드러났고, 지금은 104개입니다.

이 168 이라는 숫자에도 이야기가 있습니다. 규칙을 켜기 전에는 손으로 grep 해서 «data 를 직접 부르는 화면이 3개» 라고 알고 있었습니다. 규칙을 켜면서 예외 목록을 **규칙 자신의 판정으로** 뽑았더니 168개가 나왔습니다. 정규식으로 뽑았다면 일부가 빠졌을 것입니다.

## 되돌린 시도 다섯

옮기면서 되돌린 것도 있습니다.

1. **로그인을 `useApiQuery` 로 옮겼다가 앱이 죽었습니다.** `useApiQuery` 가 인증 Store 를 부르고, 인증 Store 가 세션 API 를 부르고, 세션 API 가 다시 `useApiQuery` 를 부르는 순환이 생겼습니다. 타입 검사와 빌드는 런타임의 훅 순환을 잡지 못합니다. 같은 날 되돌렸고, 세션 API 파일 머리에 «로그인을 `useApiQuery` 로 옮기지 마라» 를 적어 두었습니다. 공용 네트워크 유틸을 쓰는 마지막 1개가 바로 이 로그인입니다.
2. **인텐트 화면의 옛 코드를 한 번에 걷어 내려다 되돌렸습니다.** 새 화면이 준비됐다고 보고 옛 거대 화면을 지웠다가, 같은 날 원래대로 돌렸습니다. 사용자 지시는 «옛 화면은 그대로 두고, 새 화면은 따로 들어가는 주소로만» 이었습니다.
3. **한 Business Flow 가 남의 영역까지 규칙을 넓히려다 철회했습니다.** 다른 기능에 예외 항목을 만들고 빌드를 한 번 깨뜨렸습니다. 사용자 지적은 «리팩터링은 지정한 곳만» 이었습니다.
4. **로컬 데몬에 관리자 토큰을 넘기는 방식을 걷었습니다.** 데몬은 AI 에이전트를 도구 전부 · 승인 없이 띄우는 곳이라, 계정 권한 전체를 가진 토큰을 가장 믿을 수 없는 곳에 두게 되기 때문입니다.
5. **리팩터링 중에 고친 기존 버그를 되돌렸습니다.** 두 번 있었습니다. 리팩터링 Business Flow 는 동작을 바꾸지 않는다는 원칙 때문입니다. 버그는 따로 고칩니다.

## 줄지 않은 것

감추지 않고 적어 둡니다. **큰 파일은 줄지 않았습니다.**

거대 컴포넌트 둘은 사라졌습니다. 대신 **ViewModel 이 새 거대 파일이 됐습니다.** 지금 1,000줄이 넘는 파일 3개가 모두 ViewModel 이고, 가장 큰 것은 2,000줄이 넘습니다. 500줄이 넘는 파일은 오히려 두 배 가까이 늘었습니다(약 19개 → 약 35개). 화면의 판정을 ViewModel 한 곳에 모으는 규칙이 효과를 낸 만큼, 그 한 곳이 커진 것입니다. 큰 ViewModel 을 어떻게 나눌지는 아직 정하지 못했습니다.

## 아직 남은 것

| 남은 것 | 크기 |
| --- | --- |
| feature 가 data 를 직접 부르는 예외 | 104개 파일 |
| feature 가 module 의 에러 파일을 직접 부르는 예외 | 31개 파일 |
| 공용 네트워크 유틸 사용 | 1개 파일(로그인) |
| module 표면에 남은 `isLoading` | 78개 파일 (새 규칙은 앞으로 쓰는 코드에만 적용) |
| `src/component/` 에 남은 파일 | 2개 |
| 사람 리뷰로만 지키는 규칙 | 상태 단계 · 판정 재계산 금지 등 여럿 |

예외 목록은 줄어들기만 합니다. 목록 길이를 테스트가 고정해 두어서, 늘리는 수정은 테스트가 막습니다.

## 정리

- 한 번에 갈아엎지 않고 **기능 하나 = Business Flow 하나**, 그 안을 조각으로 나눠 옮겼습니다. 마지막 조각은 늘 옛 코드 제거입니다.
- `component/` 203 → 2, 네트워크 유틸 직접 사용 35 → 1, 테스트 1 → 511. 같은 기준으로 센 값입니다.
- 되돌린 것이 다섯 번 있었고, **큰 파일은 오히려 늘었습니다.** 아직 옮기는 중입니다.
